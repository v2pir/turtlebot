01 — Launch

What happens when you run sim.py

You type python3 scripts/sim.py and the entire simulation starts. Here's every step.

The Symlink Trick

TurtleBot4's Gazebo launcher only looks for world files in one specific system directory: /opt/ros/jazzy/share/turtlebot4_gz_bringup/worlds/. Our world file lives in our repo at cuttlefish_sim/sim_gazebo/worlds/cuttlebot_world.sdf. So we create a symlink — a shortcut — from the system directory pointing to our file.

sim.py : 37-41 system_worlds = "/opt/ros/jazzy/share/turtlebot4_gz_bringup/worlds" link_path = os.path.join(system_worlds, WORLD_NAME + ".sdf") if not os.path.exists(link_path): subprocess.run(["sudo", "ln", "-sf", world_sdf, link_path], check=True)

ln -sf means: -s = symbolic link (not a copy, a pointer), -f = force (overwrite if it already exists). sudo is needed because it's a system directory. This only runs once — the if not os.path.exists check skips it after that.

The Gazebo Command

sim.py : 44-50 gazebo_cmd = [ "ros2", "launch", "turtlebot4_gz_bringup", "turtlebot4_gz.launch.py", f"world:={WORLD_NAME}", # use our custom world "slam:=true", # build map + track position "nav2:=true", # path planning + driving "rviz:=true", # graphical visualization window ]

Let's break down each piece:

ros2 launch vs ros2 run

ros2 run starts a single node — one program. ros2 launch runs a launch file that can start dozens of nodes at once with configuration. The TurtleBot4 launch file starts the Gazebo simulator, spawns the robot model, starts all sensor plugins, and creates the ROS 2 bridge between Gazebo and ROS topics.

world:=cuttlebot_world — what this means

This is a ROS 2 launch argument. It tells the launch file to load our cuttlebot_world.sdf instead of the default warehouse world. Because we symlinked our file into the system worlds directory, Gazebo can find it by name.

slam:=true — Simultaneous Localization and Mapping

SLAM builds a map of the room as the robot drives around using its lidar sensor, and simultaneously tracks where the robot is on that map. It outputs an occupancy grid (each pixel = free/wall/unknown) and publishes the robot's estimated pose.

nav2:=true — Navigation 2 Stack

Nav2 is the path planner. When you tell the robot "go to (2.5, 1.5)", Nav2 plans a collision-free path around walls and obstacles, sends velocity commands to the wheels to follow that path, and continuously re-plans if the robot drifts. It includes: a global planner (full path), a local controller (smooth driving), costmaps (obstacle avoidance layers), and recovery behaviors (what to do if stuck).

rviz:=true — Visualization

Opens RViz, a graphical window that shows you the map, the robot's position as a dot, the planned path as a line, laser scan points, costmap layers, etc. Purely for observation — it doesn't affect the simulation.

Background Process

subprocess.Popen(gazebo_cmd) starts Gazebo as a background process. Popen means "start this and keep going." If we used subprocess.run() instead, it would block — sim.py would freeze on that line until Gazebo exits, and we'd never launch the experiment nodes.

The 15-Second Wait

sim.py : 64-65 print(f"waiting {GAZEBO_STARTUP_DELAY}s for gazebo and nav2 to start...") time.sleep(GAZEBO_STARTUP_DELAY) # 15 seconds

Gazebo + Nav2 needs time to initialize: loading the world, spawning the robot, starting sensor plugins, building costmaps. 15 seconds is a rough estimate. After the wait, we check gz_proc.poll() — if it returns None, Gazebo is still alive. If it returns a number, it already crashed.

Node Launch Order

The three experiment nodes launch in a specific order with 1-second gaps:

1 location_awareness

Starts publishing zone data. Must be running before the state manager needs it.

2 brain_node

Starts listening for trial commands. Must be ready before the state manager sends any.

3 state_manager

The conductor. Launches last because it depends on the other two being ready.

The Shutdown Sequence

When you press Ctrl+C, Python catches KeyboardInterrupt. The finally block kills everything in reverse order:

sim.py : 96-111 finally: # kill everything in reverse order for name, proc in reversed(processes): if proc.poll() is None: proc.send_signal(signal.SIGINT) # like Ctrl+C on each one # give 5 seconds for graceful exit for name, proc in processes: try: proc.wait(timeout=5) except subprocess.TimeoutExpired: proc.kill() # hard kill (SIGKILL)

Reverse order: state_manager first (stop the experiment), then brain, then location, then gazebo. SIGINT is the polite "please stop" signal (same as Ctrl+C). .kill() is the hard "you're dead now" signal — used only if a process ignores SIGINT for 5 seconds.

02 — The Room

cuttlebot_world.sdf

The physical space the robot lives in. Defined in SDF (Simulation Description Format) — XML that tells Gazebo what to render.

Room Layout — 8m x 6m, origin at center

Dashed lines show the zone boundaries that location_awareness.py uses. The dashed cyan paths show the routes the robot takes to reach each chamber — through the gap in the divider.

The Walls

Four box models, 0.15m thick, 2.5m tall. Each wall has both a <collision> (physics — things bounce off it) and a <visual> (what you see). The pose 0 3.075 1.25 0 0 0 means: x=0, y=3.075, z=1.25 (halfway up the 2.5m wall), with no rotation.

The Divider Wall

Two segments at y=0 that split the room in half. The left segment is centered at x=-2.3 (3.4m wide), the right at x=2.3 (also 3.4m wide). Between them is a 1.2m gap from about x=-0.6 to x=0.6. This gap is the doorway — the only way the robot can get from the south half (center) to the north half (chambers).

Chamber Markers

Two flat colored squares on the ground — only 0.02m tall (basically painted on the floor). Blue at (-2.5, 2.5) for the left chamber, red at (2.5, 2.5) for the right. They have <visual> only, no <collision> — the robot drives right over them. They're just visual cues so you can see where the chambers are in Gazebo.

Physics Engine & Plugins

The physics engine is ODE (Open Dynamics Engine) with a 3ms step size — every 3 milliseconds, the engine recalculates all positions and forces. real_time_factor=1.0 means 1 second of sim = 1 second of real time.

The 4 plugins: Physics (runs the physics engine), UserCommands (lets you spawn/delete things at runtime), SceneBroadcaster (sends scene data to GUIs), Contact (detects when things touch).

03 — Location Awareness

location_awareness.py

Tracks where the robot is and publishes which zone it's in. The eyes of the experiment.

How ROS 2 Nodes Work

A ROS 2 node is a program that communicates with other programs through topics. A topic is a named channel — like a radio station. One node publishes messages to a topic, other nodes subscribe and receive them.

Messages arrive through callbacks — functions that get called automatically when a new message arrives. rclpy.spin(node) is the event loop that sits forever, waiting for messages or timers to fire, and calls the appropriate callbacks. Nothing happens in a node unless spin is running.

this node's connections

Subscribes to: /amcl_pose (map position) and /odom (wheel odometry)
Publishes to: /carl/zone (which zone the robot is in)

AMCL vs Odometry

AMCL (Adaptive Monte Carlo Localization) uses the lidar + the map to figure out where the robot is. It scatters thousands of "particles" across the map, each guessing "maybe the robot is here", then compares what the lidar sees vs what each particle would see. Particles that match well survive, bad guesses die. Over time, the particles converge on the robot's true position. This is accurate but requires a map.

Odometry counts wheel rotations to estimate how far the robot has moved. Left wheel turned 100 times, right wheel turned 102 times → we went roughly forward and slightly right. It's always available but drifts over time — small errors accumulate, and after a few minutes the estimate can be meters off.

location_awareness.py : 57-64 def odom_callback(self, msg): # use odometry if amcl data doesnt exist if self.source == 'amcl': return # ignore odom when AMCL is available self.x = msg.pose.pose.position.x self.y = msg.pose.pose.position.y self.yaw = self.quaternion_to_yaw(msg.pose.pose.orientation) self.source = 'odom' self._publish_zone()

AMCL is preferred because it's absolute (tied to the map). If AMCL has published at least once, self.source gets set to 'amcl' and odom callbacks are ignored via the early return.

Quaternion to Yaw

Rotations in 3D are represented as quaternions — four numbers (x, y, z, w) that encode a rotation. For a robot on a flat floor, we only care about yaw — which direction it's facing, like a compass.

location_awareness.py : 92-95 def quaternion_to_yaw(self, q): siny_cosp = 2.0 * (q.w * q.z + q.x * q.y) cosy_cosp = 1.0 - 2.0 * (q.y * q.y + q.z * q.z) return math.atan2(siny_cosp, cosy_cosp)

atan2 converts (y, x) components into an angle in radians. The formulas above extract the yaw component from the quaternion. If the robot faces north (positive y), yaw = ~1.57 rad (90 degrees). Facing east, yaw = 0. Facing south, yaw = -1.57.

Zone Detection

The room is divided into four zones based on coordinates:

location_awareness.py : 67-78 def _compute_zone(self): if self.y < 0.5: # south half return 'CENTER' elif self.x < -1.0 and self.y > 0.5: # far left, past divider return 'LEFT_CHAMBER' elif self.x > 1.0 and self.y > 0.5: # far right, past divider return 'RIGHT_CHAMBER' else: # near the gap return 'DIVIDER'

The boundary at y=0.5 separates the south half (center area) from the north half (chambers). The boundaries at x=-1.0 and x=1.0 separate left chamber from right chamber. Anything in the north half between those x values is the DIVIDER zone (near the gap).

Publishing the Zone

location_awareness.py : 80-89 def _publish_zone(self): zone = self._compute_zone() if zone != self.current_zone: # only log when zone changes self.current_zone = zone self.get_logger().info(f'Zone changed: {zone}') msg = String() msg.data = json.dumps({'zone': zone}) # e.g. {"zone": "CENTER"} self.zone_pub.publish(msg)

Called on every odom update (~20-50 times/sec). Publishes a JSON string to /carl/zone. The state manager subscribes to this to know where the robot is.

04 — The Q-Learning Math

delayed_gratification.py

The mathematical brain of the experiment. No ROS, no robot — pure math that decides what the cuttlefish would do.

The Q-Table

A 4 x 2 grid of numbers. 4 states (rows), 2 actions per state (LEFT, RIGHT). Each number is a Q-value — the agent's estimate of "how good is this action in this state?" Starts at all zeros.

State Description Q(LEFT) Q(RIGHT) Correct
EXPM_LR live shrimp LEFT, dead shrimp RIGHT 0.00 0.00 LEFT
EXPM_RL dead shrimp LEFT, live shrimp RIGHT 0.00 0.00 RIGHT
CTRL_LR unobtainable LEFT, dead shrimp RIGHT 0.00 0.00 RIGHT
CTRL_RL dead shrimp LEFT, unobtainable RIGHT 0.00 0.00 LEFT

The EXPM states are experimental — they test delayed gratification (live vs dead). The CTRL states are control — they test basic discrimination (dead vs unobtainable). In each trial, one of these states is randomly selected (25% chance each).

Rewards

live shrimp

5.0

dead shrimp

1.0

unobtainable

0.0

The Q-Update Rule

After every trial, the Q-value for the chosen (state, action) pair gets updated:

Q-Update Equation
Q(state, action) = Qold + α × (reward − Qold)
where α = 0.10 (learning rate)

This nudges the Q-value toward the actual reward by 10% each time. Let's trace an example for state EXPM_LR, action LEFT (reward = 5.0):

Worked Example — Learning Live Shrimp Value
Trial 1: Q = 0.00 + 0.10 × (5.0 − 0.00) = 0.50
Trial 2: Q = 0.50 + 0.10 × (5.0 − 0.50) = 0.95
Trial 3: Q = 0.95 + 0.10 × (5.0 − 0.95) = 1.355
Trial 4: Q = 1.355 + 0.10 × (5.0 − 1.355) = 1.72
...
Trial 20: Q ≈ 4.32 (slowly approaching 5.0)

With α=0.10, the Q-value approaches the true reward exponentially — fast at first, then slowing down. It never quite reaches 5.0 because each step only closes 10% of the remaining gap.

Softmax Action Selection

The agent doesn't always pick the highest Q-value — it uses a probability distribution. Higher Q-values are more likely to be chosen, but there's always some randomness.

delayed_gratification.py : 84-107 def action_select(q, beta): # sum of e^(β × Q) for all actions sum_softmax = sum(exp(beta * q[i]) for i in range(len(q))) r = random.random() # random number 0 to 1 cumulative = 0.0 for i in range(len(q)): cumulative += exp(beta * q[i]) / sum_softmax if cumulative >= r: return i # pick this action return len(q) - 1 # fallback (shouldn't happen)
Worked Example — Softmax with β=1.0
Say Q-values are: q = [4.3, 0.85] (EXPM_LR after training)

Step 1: Exponentiate
e^(1.0 × 4.3) = 73.7
e^(1.0 × 0.85) = 2.34

Step 2: Sum
73.7 + 2.34 = 76.04

Step 3: Probabilities
P(LEFT) = 73.7 / 76.04 = 96.9%
P(RIGHT) = 2.34 / 76.04 = 3.1%

Step 4: Roll random number. If r < 0.969 → LEFT, else → RIGHT

The β (beta) parameter controls greediness. β=0 means completely random (50/50). β=∞ means always pick the best. β=1.0 is a moderate setting where the agent usually picks the better option but occasionally explores.

The Patience Function — prob_wait()

This converts a delay (in seconds) into a number between 0 and 1 that represents "how patient is the agent?"

delayed_gratification.py : 71-82 def prob_wait(tim): mean = 70 std_dev = 20 beta_weight = 2 pw = 1 / np.exp(beta_weight * norm.cdf(tim, loc=mean, scale=std_dev)) return pw

Two parts to understand:

Part 1: norm.cdf(tim, mean=70, std=20) — this is the cumulative normal distribution. It's an S-shaped curve centered at 70 with spread 20. It takes a time value and returns a number between 0 and 1:

norm.cdf values
delay = 10s: norm.cdf(10, 70, 20) = 0.0013 (very small — barely started)
delay = 50s: norm.cdf(50, 70, 20) = 0.159 (starting to grow)
delay = 70s: norm.cdf(70, 70, 20) = 0.500 (exactly at the mean)
delay = 100s: norm.cdf(100, 70, 20) = 0.933 (almost saturated)
delay = 130s: norm.cdf(130, 70, 20) = 0.999 (basically 1)

Part 2: 1 / exp(2 × cdf_value) — takes that 0–1 value and converts it to patience:

Full prob_wait calculation
delay = 10s: 1/exp(2 × 0.0013) = 1/exp(0.003) = 0.997 almost full patience
delay = 50s: 1/exp(2 × 0.159) = 1/exp(0.318) = 0.728 still pretty patient
delay = 70s: 1/exp(2 × 0.500) = 1/exp(1.0) = 0.368 starting to give up
delay = 100s: 1/exp(2 × 0.933) = 1/exp(1.866) = 0.155 very impatient
delay = 130s: 1/exp(2 × 0.999) = 1/exp(1.997) = 0.136 almost no patience

Short delay → patience near 1.0 → Q-values barely discounted → agent picks live shrimp.
Long delay → patience near 0 → live shrimp Q-value gets crushed → agent settles for dead shrimp.

The Patience Discount

This is the key mechanism. When the agent faces a choice, p_wait multiplies the Q-value of the live shrimp option only:

delayed_gratification.py : 133-140 # copy q-values so patience discount doesn't change the table q = list(qtable.get_row(current_state)) # apply patience discount (live shrimp states only) if current_state == EXPM_LR: q[LEFT] *= p_wait # live shrimp is on the LEFT elif current_state == EXPM_RL: q[RIGHT] *= p_wait # live shrimp is on the RIGHT
Example — delay 70s, EXPM_LR state (live LEFT, dead RIGHT)
Q-table says: Q(LEFT) = 4.3, Q(RIGHT) = 0.85
p_wait at 70s: 0.368

After discount: Q(LEFT) = 4.3 × 0.368 = 1.58, Q(RIGHT) = 0.85 (unchanged)

Now softmax sees: P(LEFT) = e^1.58 / (e^1.58 + e^0.85) = 4.86 / (4.86 + 2.34) = 67.5%
Before discount it was 96.9%. Now it's only 67.5% — the agent is wavering.

Control states (CTRL_LR, CTRL_RL) are never discounted. The unobtainable shrimp stays at 0.0 regardless of delay, so patience doesn't affect those choices.

Why Copy Q-Values First

bug fix from carl

The original CARL code did q = qTbl (reference, not copy) then q[LEFT] *= p_wait — this permanently mutated the Q-table. Every trial would further reduce the live shrimp Q-value, corrupting the learned values. Our code does q = list(qtable.get_row(...)) which makes an independent copy. The discount only affects the decision, not the stored knowledge.

After Training — What the Q-Table Looks Like

After 100 training trials (p_wait=1.0, no discount), the table converges to approximately:

StateQ(LEFT)Q(RIGHT)Interpretation
EXPM_LR ~4.30 ~0.85 learned: left (live) is way better
EXPM_RL ~0.85 ~4.30 learned: right (live) is way better
CTRL_LR ~0.00 ~0.90 learned: right (dead) is better than nothing
CTRL_RL ~0.90 ~0.00 learned: left (dead) is better than nothing

Values don't reach exactly 5.0 or 1.0 because: (a) learning is only 10% per step, (b) softmax sometimes picks the wrong action, so both columns get some updates, (c) 100 trials isn't enough to fully converge. But the relative ordering is clear — the agent knows which side is better in every state.

05 — The Brain

brain_node.py

A thin ROS 2 wrapper around the Q-learning library. Receives commands, makes decisions, sends results.

What It Holds

brain_node.py : 27-36 class BrainNode(Node): def __init__(self): super().__init__('brain_node') self.qtable = QTable() # 4x2 grid, all zeros self.trial_count = 0 self.result_pub = self.create_publisher(String, '/carl/trial_result', 10) self.cmd_sub = self.create_subscription( String, '/carl/trial_cmd', self.trial_callback, 10)

The brain holds one QTable that persists across all trials — this is where learning accumulates. The 10 in the publisher/subscriber is the queue depth — how many messages to buffer before dropping old ones.

The Trial Callback

Every time a message arrives on /carl/trial_cmd, this function runs:

1 Parse the JSON command

{"p_wait": 0.368} or {"p_wait": 1.0, "state": 2}. The p_wait field is required. The state field is optional — if omitted, run_trial picks a random state.

2 Run Q-learning trial

Calls run_trial(self.qtable, p_wait, forced_state=...). This picks a state, copies Q-values, applies patience discount, does softmax selection, determines reward, updates Q-table. Returns (reward, is_experimental, state, action).

3 Check correctness

is_correct(state, action) returns True if the agent picked the higher-reward option. For EXPM_LR that means LEFT, for CTRL_RL that means LEFT, etc.

4 Publish result

Sends JSON to /carl/trial_result:

Message format // Command (state_manager → brain) {"p_wait": 0.368, "state": null} // Result (brain → state_manager) { "state": 0, // EXPM_LR "action": 1, // RIGHT "reward": 1.0, // dead shrimp (wrong choice) "is_experimental": true, // EXPM state "correct": false, // should have gone LEFT "trial": 142 // running count }

Every 25 trials, the brain prints the full Q-table to the console so you can watch the values evolve during the experiment.

06 — The Experiment

state_manager.py

The conductor. Orchestrates training, testing, navigation, and result collection.

TurtleBot4Navigator

A library from Clearpath that wraps Nav2's raw action servers into simple Python methods:

getPoseStamped(coords, direction)

Creates a ROS PoseStamped message — a position [x, y] plus an orientation (NORTH, SOUTH, etc.) converted to a quaternion. This is the "goal" you hand to Nav2.

startToPose(goal)

Tells Nav2 "go here." Nav2 plans a path, drives the robot, avoids obstacles. This call blocks until the robot arrives (or fails). This is why each trial takes real time.

waitUntilNav2Active()

Blocks until Nav2's action servers are ready. Called once at startup — doesn't matter how long Gazebo takes to start, this waits.

Navigation Coordinates

CENTER: (0.0, -1.5)
LEFT: (-2.5, 1.5)
RIGHT: (2.5, 1.5)

The Timer Trick

state_manager.py : 73-75 # run experiment in a timer callback to not block the constructor self.create_timer(2.0, self.run_experiment_once) self.experiment_started = False

Why not just run the experiment in __init__? Because the constructor needs to finish so that rclpy.spin() can start. If we ran the experiment inside the constructor, the node's subscribers wouldn't be active yet — we'd publish commands but never receive results. The 2-second timer lets the constructor finish, spin starts, and then the experiment begins.

send_trial_cmd — The Synchronous-Over-Async Pattern

state_manager.py : 87-110 def send_trial_cmd(self, p_wait, forced_state=None): # build and publish the command self.last_result = None self.waiting_for_result = True msg = String() msg.data = json.dumps({'p_wait': p_wait}) self.cmd_pub.publish(msg) # spin until we get a result (with timeout) timeout = time.time() + 10.0 while self.waiting_for_result and time.time() < timeout: rclpy.spin_once(self, timeout_sec=0.1) return self.last_result

ROS 2 is asynchronous — you publish a message and callbacks arrive whenever. But the experiment needs to be sequential (send command, wait for answer, then navigate). So we use spin_once() in a loop — this processes one incoming message (or waits 0.1s) on each iteration. When result_callback fires, it sets self.waiting_for_result = False and the loop exits. There's a 10-second timeout in case the brain is dead.

Phase 1: Training

100 trials — no robot movement

The robot sits still. The state manager fires 100 trial commands at the brain with p_wait=1.0 (no patience discount). The brain runs Q-learning each time, learning which Q-values should be high and low. This takes a few seconds total.

state_manager.py : 139-170 def run_training_phase(self): state_total = np.zeros(STATES) # [0, 0, 0, 0] state_hits = np.zeros(STATES) # [0, 0, 0, 0] for t in range(TRAINING_TRIALS): # 100 times result = self.send_trial_cmd(p_wait=1.0) s = result['state'] state_total[s] += 1 # count per state state_hits[s] += int(result['correct']) # log every 25 trials if (t + 1) % 25 == 0: # prints: "Training 25/100: EXPM_LR=80%, EXPM_RL=75%, ..."

By the end, accuracy per state is typically 80-95%. Not 100% because softmax is probabilistic — even with good Q-values, the agent sometimes explores the wrong action.

Phase 2: Testing

This is where the robot moves. 13 delays (10, 20, ... 130 seconds), 20 trials per delay.

1 Navigate to CENTER

Robot drives to (0, -1.5) — the starting position in the south half of the room.

2 For each delay (10s, 20s, ... 130s)

Calculate p_wait = prob_wait(delay). For 10s → 0.997, for 70s → 0.368, for 130s → 0.136.

3 Send trial command to brain

Brain picks a random state, applies patience discount, chooses LEFT or RIGHT.

4 Navigate to chosen chamber

If action=LEFT → drive to (-2.5, 1.5). If action=RIGHT → drive to (2.5, 1.5). The robot goes through the gap in the divider wall, turns, and drives to the chamber. Nav2 handles pathfinding.

5 Record & return to CENTER

Record whether it was correct (experimental: chose live shrimp? control: avoided unobtainable?). Then drive back to (0, -1.5) for the next trial.

total robot trips

13 delays × 20 trials × 2 navigations (to chamber + back to center) = 520 navigation actions. Each navigation takes the robot through the gap and across the room. This is the slow part of the experiment.

Recording Results

state_manager.py : 200-212 # for experimental trials: did it choose live shrimp? if is_exp: exp_total += 1 exp_correct += int(reward > DEAD_RWD) # reward > 1.0 means live shrimp (5.0) else: ctrl_total += 1 ctrl_correct += int(reward > UNOBTAINABLE_RWD) # reward > 0.0 means dead shrimp (1.0)

For experimental trials: "correct" means it chose the live shrimp (reward 5.0 > 1.0). For control trials: "correct" means it chose dead shrimp over unobtainable (reward 1.0 > 0.0).

Saving Results

After all 360 trials (100 training + 260 testing), everything is saved to cuttlefish_sim/sim_gazebo/results.json:

"130": [...] // 20 entries for delay=130s }, "delays": [10, 20, 30, ..., 130], "params": {"training_trials": 100, "testing_trials_per_delay": 20} }

the big picture

This experiment proves that a simple Q-learning agent with a patience discount can reproduce the delayed gratification behavior observed in real cuttlefish. The robot is the cuttlefish. The chambers are the shrimp. The prob_wait() function is the biological patience mechanism modulated by serotonin and hunger. The math is identical — we just put it on wheels.
